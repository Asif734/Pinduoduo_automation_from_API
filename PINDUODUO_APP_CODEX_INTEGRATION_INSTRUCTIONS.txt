Use ISO-8601 instants with Z or an explicit offset, preferably UTC. Convert China/Dhaka/other local times correctly; do not relabel them with Z. 6. IMAGES AND VIDEO FRAMES

Use multipart/form-data for new images/frames:

- Repeated FILE fields named images, in exactly the media-array order.
- Let the HTTP library encode the multipart boundary. Do not hand-set an incomplete Content-Type boundary or send images="string"/an empty dummy item.
- A bounded Content-Length is required by hosted upload admission (maximum complete body 55 MiB). Use an upload API that can calculate/set the real body size; unbounded chunked uploads are not supported by this admission contract.

Media entry, exactly:
{ "id":"stable-media-id", "messageId":"owning-message-id", "kind":"image", "label":"optional short description" }

{ "id":"stable-frame-id", "messageId":"owning-video-message-id", "kind":"frame", "label":"video-1 frame 00:12.500", "timestampMs":12500 }

Each new media ID must occur in exactly ONE message's mediaIds; messageId must identify that same row. Files and manifest lengths/order must match. Stable media IDs cannot be reassigned to another message or changed bytes. Prefer preserving a source event ID for a video and separate stable frame IDs for its sampled frames.

Limits: up to 50 files/request; PNG/JPEG/WebP only, matching real file bytes/MIME; <=20 MiB each and <=50 MiB combined. Timestamp is an integer in milliseconds relative to the original video's start, not upload time or Unix time. Keep the app's existing <=5-minute video policy if present; current local media validation also caps timestampMs at 24 hours even though the hosted schema permits larger safe integers. Raw MP4/audio is not accepted. Extract representative chronological frames locally using existing capture/frame extraction, with overall coverage plus useful scene/action changes. Do not reupload it under a new ID, include it as a new media entry without its owning message, or attach every historical image by default. New media goes in media + images; old relevant retained media goes in referencedMediaIds. Use explicit selection/recency and existing context to minimize unrelated image loading.

There are no structured mediaSources/transcriptions fields in the current public contract. Preserve existing local transcription data. If existing product requirements need transcript transport, agree a contract separately; do not silently discard it or invent an accepted field. For an explicitly approved text-based adaptation, it can only be ordinary untrusted, correctly associated message text within existing limits, never trusted replyInstructions; do not implement that adaptation silently.

7. ACCEPTANCE, PARALLEL WORK AND POLLING

HTTP 202 acceptance returns jobId/status/createdAt/updatedAt/platform/storeId/customerUid/historyVersion/pollUrl. Persist it before proceeding. An identical request retry can return the original already-completed job in this same acceptance envelope.

Use the returned pollUrl after verifying HTTPS origin, Pinduoduo V2 path, expected jobId and storeId. Never forward the key to a different origin/redirect. Do not use the Qianniu path returned by an old client template.

Run independent per-job polling (normally every 1.5..3 seconds with jitter). One in-flight poll per job, no tight loop, and a global modest HTTP concurrency limit. Different customers' completed answers must be processed immediately: customer B must not wait for A's longer generation. A shared polling scheduler can multiplex jobs fairly; it must not await one entire job before checking others.

Serialize generations and action execution for the SAME customer scope. Freeze later messages into a separate next batch; reconcile the previous reply's actual Send/history before constructing the next one. This prevents duplicate replies and outdated troubleshooting context. Different customers can progress concurrently, subject to current server capacity.

Pinduoduo currently uses the shared Windows scheduler and borrows the JD execution group. Do not advertise four independent permanently running Pinduoduo CLIs. Neither /status active nor queued is a guaranteed process count. Start with at most TWO concurrent body uploads (current PDD admission limit); accepted jobs may progress/poll concurrently beyond two. Do not cap all outstanding jobs at the number of active uploads. Honor 429/backoff, and avoid unbounded requests/frames.

Use separate timeout concepts:
- Status/poll/small JSON HTTP attempt: typically about 30 seconds.
- Multipart upload attempt: size/network-aware and bounded (e.g. 60..300 seconds), not a universal 30-second limit for a large body.
- Overall job wait: separately adjustable, e.g. 10 minutes including queueing. Deadline expiry means pending/recovery-needed to the client, not permission to replace the job.
These are CLIENT recommendations, not promises of server deadlines. Preserve durable pending state and allow later recovery. Do not mark a model failure solely because a local wait timer ended.

Job states:
queued / processing: pending; keep polling.
completed: generated draft ready for binding and app checks.
failed: terminal generation failure; inspect error.code, do not automatically regenerate indefinitely.
recovery_required: keep/recover the original job by bounded polling; never mint a fresh key to bypass uncertain old execution.
expired or HTTP 410: result no longer available; old key remains reserved. Reconcile before any explicitly justified new task.

8. FROZEN OUTBOX AND RESTART RECOVERY

Before FIRST POST, durably save namespace, frozen target IDs, all messages, full replyInstructions, historyVersion, stable idempotencyKey (UUID), serialized request, immutable visuals and app task state. One logical batch gets ONE key.

POST acceptance lost / network timeout / app crash with no jobId: replay the SAME frozen logical request and files/key with bounded backoff. Never update IDs/timestamps/policy or split the accepted batch during transport recovery.
Known jobId: poll that job, including after restart. Do not POST a fresh job just because polling timed out.
Persist received result/binding/digest before actual customer Send. Generation recovery and Send recovery are separate ledgers.

429/network/transient 503: bounded exponential backoff with jitter and Retry-After when supplied. Preserve the original request identity. Do not retry 400/401/403/409/413/415 unchanged forever. For validation/config errors, stop this task safely and show an actionable operator error.

Some Pinduoduo errors intentionally retain the QIANNIU_ prefix because the implementation shares the V2 contract. Do not reject/rewrite such errors just because the prefix is not PINDUODUO_. Important examples:
- 401 UNAUTHORIZED: wrong/missing PDD key; configuration repair.
- 403 QIANNIU_STORE_FORBIDDEN: unauthorized store; do not guess a new store.
- 400 QIANNIU_INVALID_REQUEST / QIANNIU_INVALID_MESSAGE / QIANNIU_INVALID_TARGET / QIANNIU_INVALID_MEDIA_BINDING: fix protocol/event mapping.
- QIANNIU_REPLY_INSTRUCTIONS_REQUIRED / QIANNIU_INVALID_REPLY_INSTRUCTIONS: supply the full nonempty string.
- 413 QIANNIU_REPLY_INSTRUCTIONS_TOO_LARGE / QIANNIU_JSON_TOO_LARGE / FILE_TOO_LARGE / QIANNIU_MEDIA_TOO_LARGE / QIANNIU_INVALID_BODY_SIZE: validate real byte limits. Never silently truncate a frozen request.
- 415 QIANNIU_INVALID_MEDIA / QIANNIU_INVALID_CONTENT_TYPE: fix actual MIME/encoding.
- 429 QIANNIU_UPLOAD_BUSY / QIANNIU_QUEUE_FULL / QIANNIU_CONTROL_BUSY: bounded backoff; distinct from model-provider limits.
- 503 AGENT_OFFLINE / AGENT_UPGRADE_REQUIRED / QIANNIU_CONTEXT_DISABLED / QIANNIU_LEDGER_UNAVAILABLE: readiness/recovery, not customer fault.
- 503 QIANNIU_ORDER_CONTEXT_UNAVAILABLE: do not silently strip facts from an uncertain accepted request. Verify capability before a genuinely new batch.
- 409 QIANNIU_IDEMPOTENCY_CONFLICT: same key, changed fingerprint; investigate stored batch. Do not evade it with a new UUID.
- Other job errors, including CODEX_FAILED, must keep their recorded code. Do not infer account, network or image failure without evidence.

Use max-attempts/time budgets; keep exhausted uncertain tasks parked/recoverable. Never resend customer text as a side effect of a transport retry.

10. ACTUAL SEND AND DELIVERY ACK (REQUIRED FOR CORRECT HISTORY/MONITOR)

Keep a durable execution ledger keyed by namespace + jobId + resultDigest. Recheck the correct Pinduoduo account/store/customer immediately before Send. Marking a draft completed, filling the input box, or clicking Send does NOT prove sent. Verify a reliable native platform Send acknowledgement/message ID or an unambiguous newly sent matching row for this customer. Customer read receipt is not required and must not be claimed.

After verified Send, POST /replies/{jobId}/delivery with application/json:
{
 "storeId":"pinduoduo-default",
 "eventId":"<DURABLY_PERSISTED_NEW_DELIVERY_EVENT_ID>",
 "status":"sent",
 "occurredAt":"<ACTUAL_EVIDENCE_TIME_ISO_8601>",
 "resultDigest":"<EXACT_DIGEST_FROM_THIS_COMPLETED_RESULT>",
 "actualSentText":"<EXACT_TEXT_REALLY_SENT_TO_THIS_CUSTOMER>"
}

actualSentText is optional, nonempty, <=10,000 characters, ONLY with sent. Include it when the app's policy guards changed the final text so server history reflects reality. If omitted, server records the original generated reply text. If an edited answer exceeds the supported limit, do not silently truncate/misreport it; retain the local evidence and flag the contract mismatch.

Success response is HTTP 200:
{ "jobId":"...", "storeId":"pinduoduo-default", "eventId":"...", "status":"sent", "occurredAt":"...", "resultDigest":"...", "actualSentText":"...", "recorded":true }
actualSentText is echoed only when supplied. Check matching job/event/digest/status and recorded=true. Persist ACK success. Response means durable server delivery-record acknowledgement, not a second customer Send.

Delivery meanings:
sent: reliable evidence the reply text actually left the app through the correct PDD sender.
failed: definite Send failure / confirmed not sent.
unknown: attempted Send outcome cannot yet be determined, e.g. crash/ambiguous timeout.
pending/not recorded: no delivery outcome has been acknowledged yet; normal for synthetic no-send tests. Do not fabricate sent or pretend an unattempted draft was delivered.

For unknown, reconcile platform evidence before any retry of actual Send. When later confirmed sent/failed, create a NEW delivery eventId with the newly established status/time. Do NOT mutate the old unknown event. The server supports unknown-to-confirmed transitions, and a confirmed sent result is not downgraded by a later uncertain report.

If ACK response is lost or 503 QIANNIU_DELIVERY_UNCONFIRMED occurs, retry the IDENTICAL persisted delivery event, same eventId/body/time/digest. Do not resend customer text. Same eventId with changed fields is 409 QIANNIU_DELIVERY_CONFLICT; wrong job/digest is QIANNIU_DELIVERY_RESULT_CONFLICT.

Persist the delivery outbox before posting it; recover it on app restart. Reconcile unresolved ACKs promptly, within available result retention. The hosted polling-result TTL defaults to 48 hours but is configurable; it differs from local 30-day conversation retention. Do not postpone ACKs until retention expires.

The server appends confirmed sent text to service history on sent ACK. To avoid duplicate history, do not also blindly upload the same bot-generated service row under a second native capture ID. Correlate it in the app execution ledger. Genuinely manual or different service messages still need normal synchronization with stable IDs.

For reply_then_transfer, preserve authorized transfer-adapter behavior and log text-Send and transfer outcome separately. Delivery sent describes the reply TEXT, not proof that the human handoff succeeded. Do not send unknown/failed transfer outcome as if the customer text was unsent, or invent a transfer-status API.
